## 里程碑

### 1. 全栈单仓基线与仓库安全门禁

**时间**：2026-08-03（第 1 周）

**做了什么**：把原本分散的前端源码、后端源码、发布脚本与本机运维工具收进同一个 monorepo，以一次基线提交落地约 8.5 万行；同一批引入仓库校验脚本——跟踪文件白名单、禁止目录与扩展名清单（依赖目录、构建产物、数据库文件、日志、压缩包、安装包、符号链接与子模块）、全量跟踪文本的凭据特征扫描，以及前后端两份共享产品库必须字节级同哈希的断言。同期把 CI 运行时镜像升级，并修复发布准备脚本在非 POSIX shell 下的执行告警。

**为什么做**：多份源码副本意味着构建分叉——同一份前端在不同机器上会产出不同行为，发布证明无法复现。收口到单仓之后，"源码 → 构建 → 发布证明"必须共用一条链路。

**留下什么约束**：仓库校验是常驻门禁，不是一次性清理。任何新增文件都要经过禁止清单与凭据扫描；两份共享数据文件只要字节漂移就直接失败。Windows 与 POSIX 双环境可运行从这一刻起成为默认要求，而不是可选项。

### 2. 长报告可恢复分析流水线与部署路径固定

**时间**：2026-08-04（第 1 周）

**做了什么**：为长报告（几十到上百页、需多次模型调用）建立可恢复的分块分析流水线：任务状态落盘、逐块产物暂存、失败后可从已完成的块继续；引入任务服务协议与前后端一致的任务状态判定；把上传失败收敛为闭集分类而不是一句通用报错；同时把 TLS 网关固定到与发布版本无关的稳定运行时路径，并把分析身份改为从实现源文件内容哈希推导。

**为什么做**：固定式全量重跑在长报告上代价过高，用户刷新一次就丢全部进度；而人工版本号一旦忘记递增，缓存会返回与当前代码不符的旧结果。把身份绑到源文件字节上，改代码即改身份，不需要人记得改版本。

**留下什么约束**：分析身份会随任意相关源文件与依赖锁的字节变化而轮换——这既是特性也是代价，任何"复用更早的缓存身份"都必须在设计上被拒绝。部署路径必须跨版本稳定，否则回滚会指向不存在的目录。

### 3. 前端收敛为纯浏览器 Web，证据优先分析进入主链路

**时间**：2026-08-06（第 1 周）

**做了什么**：一次清理提交删除了多端残留（安装包基线、原生运行时兼容层、推送分支、平台选择器），把客户端形态锁定为浏览器 Web，并用边界测试断言"仓库内不存在平台目录与安装包"。同一周内一次大提交（约 110 个文件、1.6 万行）把证据优先的征信分析接入主链路：新增证据账本、分析协调器、PDF 视觉层、匹配内核与确定性评分，前端同步引入决策指标、证据闸门与负债执行策略，并把详情各分区改为独立呈现。

**为什么做**：多端残留的真实成本不是"用不上"，而是构建脚本与发布入口会出现两套真相。而"先出分数、再找依据"的旧顺序无法解释任何一个对外数字，必须把顺序反过来：先建立可绑定页证据的事实，再计算指标。

**留下什么约束**：产品边界由测试锁定（唯一客户端形态是不可回退的验收标准）。任何对外发布的征信数字必须能追溯到报告页内证据、规范化事实与确定性公式；证据不足或关系冲突时停止输出结论，不做插值。

### 4. 发布身份隔离与证据记录包 v2/v3

**时间**：2026-08-13 至 08-14（第 2 周）

**做了什么**：把"发布证明"做成硬门禁——构建产物内嵌来源文件，记录构建前后 git 状态、提交号、依赖锁哈希与注入的 API 基址；打包前置条件要求工作区完全干净，产物提交号与当前 HEAD 不符、依赖锁哈希不符或 API 基址证明不匹配都直接失败。同时把仅部署后端的场景与前端测试解耦：跨层一致性测试被移到不依赖前端安装的位置。分析侧引入"证据记录包 v3"——把多账户表按行绑定成独立记录包，卡片未结总额与账户归属分离，查询窗口计分语义显式化，并为诊断输出建立安全边界。后续几天连续补齐换行断裂的账户、显式授信额度、带括号的本币金额等等价类缺口，并修复机构排序依赖宿主 locale 导致的不稳定。

**为什么做**：发布证明的价值只在"能证伪"——只要它能被跳过，它就不存在。跨层一致性测试留在后端测试目录里会让"只发后端"的正常操作无法通过安装，因此测试的归属位置本身就是部署约束。记录包的出现，是因为"整张表交给模型自己挑归属"无法证明哪一行属于哪个账户。

**留下什么约束**：构建前干净工作区是硬前置，脏树上的测试结果不能登记为通过。仅 API 部署与全量部署各有独立测试入口，二者不可互相替代。排序、比较、格式化必须显式指定 locale 与顺序，不能依赖运行环境默认值。

### 5. 缓存绑定与任务作用域加固、恢复与访问控制

**时间**：2026-08-17（第 3 周）

**做了什么**：一次约 48 个文件、6600 行的加固提交：把权威缓存、任务作用域、任务暂存拆成三个彼此隔离的 AES-256-GCM 加密域，缓存条目绑定到由租户、文档与分析身份共同导出的密钥，跨租户、跨文档、跨版本命中在设计上不可构造；机构隔离在缺证据时 fail-closed；教师端详情授权路径补齐；固定测试账号在生产环境被显式闸门拒绝；发布预检在隔离环境中运行，避免读取真实运行数据；同时补齐证据账本的健壮性与失败诊断的闭集字段。

**为什么做**：单一加密域下的缓存键一旦可预测，就存在把 A 用户的结果命中给 B 用户的可能——这类缺陷不会体现在功能测试里。恢复路径则是第二个入口：任务重放时如果不重新校验身份绑定，之前被拒的结论会重新浮现。

**留下什么约束**：三个加密域的标识字符串各自被镜像断言锁定，改其中一个必须同步改对应测试，否则确定性套件会红。加密域改名等价于解绑存量缓存——在没有历史数据的前提下才安全。任何"放宽隔离以提高命中率"的提案都必须先给出跨租户不可能命中的构造性证明。

### 6. 阶段 0 合同冻结：双模型架构落地为机器可读契约

**时间**：2026-08-17（第 3 周）

**做了什么**：一次以文档为主的提交冻结了目标架构：架构决策记录（ADR-0001）、产品增量需求、机器可读合同 JSON、合同 JSON Schema、OCR 结构化证据契约、供应商安全门禁文档。随后四次提交把合同变成可执行门禁——引入 JSON Schema 校验器（Draft 2020-12）、补齐 450 行量级的 schema 定义、建立负例夹具（故意违规的合同样本必须被拒）、把差异范围校验限定到受保护路径、并把校验步骤接入 CI。同批还收紧了扫描器对 OCR 规范化字段的容错。

**为什么做**：双模型链路的真正风险不是"模型不够准"，而是权限边界含糊——如果 OCR 输出可以被当成事实、模型置信度可以替代证据，那么后面所有测试都测不出这类错误。散文式的架构文档不能阻止这种漂移，必须把它写成机器能拒的形式。

**留下什么约束**：合同常量的版本号（`/1.0`、`/2.0`）不参与重命名或随意升级——版本变动即 fail-closed。校验器无法证明自身字节，外部信任根必须由"干净提交 + 独立完整 diff 审查 + 同一提交号的 CI"三件共同构成。阶段 0 不改变生产行为，因此任何"已上线"的表述都必须被文档显式否认。

### 7. 前端事实真相：报告身份绑定与缺失值保全

**时间**：2026-08-17（第 3 周）

**做了什么**：八个连续修复提交，围绕两个主题。其一是缺失值：把"字段缺失"从可被强制成 `0` 或空串的状态改为独立状态，前端映射层、汇总层与展示层全量重写以保留"未知"，引入严格数值工具与闭集征信状态分类，并按 500 行量级的回归测试锁定。其二是报告身份：本地持久化前校验报告 ID，存储的报告必须绑定到请求所指定的身份，云端数据回填时保留本地 ID，同一存储槽位的别名冲突被显式防护，非法身份直接 fail-closed 而不降级展示。

**为什么做**：缺失值一旦被补成 0，负债、使用率和评分都会静默偏移，而且从结果上看不出这是插值。报告身份错位则是更严重的问题——把甲的报告渲染给乙，任何"看起来对"的数字都是错的。

**留下什么约束**：`unknown` 永远不等于 `0`、`absent` 或 `not_applicable`，四者互转是回归红线。云端回填不得覆盖本地标识。任何"为了页面能渲染而给默认值"的改动都属于本类缺陷，必须用契约测试而不是目视检查来拦。

### 8. GLM-OCR 客户端与阶段 0–3 有序集成治理

**时间**：2026-08-18 至 08-19（第 3 周）

**做了什么**：从零构建一个受严格预算约束的 OCR HTTP 客户端，分四次提交递进：客户端核心（固定端点与模型、闭集请求体、安全错误五字段）、拒绝被代理的输入（在所有对象/数组/信号/传输响应边界无条件拒绝 Proxy）、有界的 HTTPS 传输（内部严格递归下降 JSON 解析器，深度/节点数/键长/数组项数都有闭集上限；编码与解码双上限；受控解压；真实的连接超时只在新建 TLS 连接或套接字复用时清除）、重试与整批阶段截止（每页总尝试恰为 2 次、仅网络错误与 408/429/500/502/503/504 自动重试、Retry-After 只在 429 且私有、单调时钟与墙上时钟分离、420 秒阶段截止取消全部在途页）、共享 FIFO 页并发池（默认与生产锁 3、代码硬上限 4、退避前释放许可并重排、每批只创建 `min(池上限, 页数)` 个 worker、批内对等取消而跨批互不影响）。同期以约 34 个文件、4700 行落地受信任的分析支持引用链：支持引用只有服务端签名可信才允许后续动作，成功终态的诊断必须为 null，发布身份显式化。最后用一次治理提交把阶段 0–3 以四次有序 `--no-ff` 合并汇入单一集成分支，并为 5 个被多个阶段同时修改的路径逐一做语义并集核验（环境变量占位符必须恰好一个、CI 工作流与根脚本清单保留并集、前端契约测试两组断言都留）。

**为什么做**：模型调用是最容易被写成"能跑就行"的一层，而它的失败模式（重试放大、并发饥饿、时钟回拨、取消泄漏、部分结果）都是生产事故。有序合并的意义在于：每个阶段的可验证性不依赖后续阶段，任一阶段可独立回滚。

**留下什么约束**：并发、超时与尝试次数是合同值而非调优参数——生产门禁必须锁回 3。自动重试只能重试同一 provider 的同一页，绝不换模型或换 OCR 供应商。集成允许的差异被闭集枚举，路径集合等于允许并集不等于内容没漂移。真实 HTTPS 调用在全部测试中必须为 0，并由进程级探针断言。

### 9. 合并后内容基线门禁：受保护 blob 锚定与可移植校验器

**时间**：2026-08-20（第 3 周）

**做了什么**：一次 squash 合并之后，"必需祖先"这一前提被切断，原先只认识独立提交与预合并树的校验器把自己 fail-closed 了。三次提交把它改造成内容基线门禁：以六个必需祖先、21 个受保护条目、两个候选覆盖层与校验器外部信任根构成闭集锚点，显式校验干净与非浅克隆，所有 Git 读取统一带 `--no-replace-objects`（替换引用可以存在但必须被忽略，不能改变祖先或 blob 判定），且模式选择不依赖分支名、环境变量或固定 HEAD。随后两轮加固：主校验器顶层只保留 Node 内建模块，全部 bootstrap 通过之后才动态 import 已被锁定的策略、Schema 校验器与本地模块，CI 中把该步骤前移到仓库校验与运维校验之前；临时仓库的依赖桥改建到所有场景仓库的共同父目录并在每次克隆后断言仓库根没有 `node_modules`（不改 `.gitignore`、不用 `.git/info/exclude`、不放宽 clean 合同）；harness 失败诊断改为固定闭集单行码，主入口用整行正则解析并与自身允许清单双向核对，未知格式一律归一为内部错误、绝不转发原始 stderr；裸 tree 对象作为 `merge-tree` 一侧在较新 Git 上可用但在旧版 Git 上不可移植，改为每轮先用固定父提交与中性身份元数据构造确定性 commit 字节再写入对象库，从而在不同 Git 版本上得到同一棵锁定树。最后以一次治理交接提交把上述冲突账本写进仓库。

**为什么做**：一次 squash 就让"历史可达"失效，说明按分支名或环境变量挑选模式的设计不可信。真正需要锚定的是内容本身，而不是形状。同理，一个校验器如果在检查内容基线之前就已经 import 了被检查的可执行文件，那么被检查对象可以在检查发生之前改变进程——这是顺序倒置的信任漏洞。

**留下什么约束**：受保护清单冻结在合并后基线提交上；受保护内容的合法演进必须走一次独立的基线切换（换基线常量、替换必需祖先、重新锁定 harness blob），而不是绕过或弱化字面检查。合并到主干必须使用普通合并，squash 会切断新基线的祖先关系。校验器与 CI 工作流自身的字节都依赖外部信任根，不能自称已被证明。跨平台门禁必须同时保留 Windows 定向验证与 POSIX 真实 Git 证据。

### 10. OCR 结构化适配器与生产 fail-closed 反馈回流

**时间**：2026-08-20 至 08-21（第 3 周）

**做了什么**：前半周补齐概要一致性：账户概要表只在其后恰好紧跟一张完整的四行官方表时才可用，要求固定行序与唯一基数——零张候选保持未知且不造 0，多张候选以概要不一致 fail-closed；活跃数复用权威的"已注销/已结清"谓词而不再用原始桶长度，总数与历史逾期行的口径保持不变。后半周分四个切片交付确定性 OCR 结构化适配器：一个手写的全流 JPEG 结构预检（只接受 SOF0/SOF2，像素/字节/标记数/宽高全部闭集上限且调用方只能收紧，校验 DQT/DHT/DRI/SOS、熵填充只接受精确 `FF 00`、重启区间必须非空且严格 `D0..D7` 循环、渐进扫描维护每分量 64 个系数状态并要求到 EOI 前 DC 覆盖）；适配器核心（同步快照自有数据输入后才跨异步边界、只接受规范 JPEG data URI、供应商区域顺序永不重排、阅读序两两判定、文本与公式块一律标 `non-record`、UTF-16 偏移逐码位覆盖恰好一次、资源上限线性早失败于第 5001 块与第 1000001 字符、canonical JSON 递归 NFC + 键排序 + 裸 SHA-256 并深冻结）；精确空白页核验（只有单一空区域页才解码，逐像素要求三通道、长度精确等于宽×高×3、每字节等于 255，解码器 `failOn: "warning"`，不设白阈值也不做裁剪启发式，页间串行以把峰值压在单页）；表格行归属证明（HTML 只接受一个小写 table、thead 一张 th 行、tbody 若干 td 行、单元格属性只允许值恰为 1 的 rowspan/colspan；Markdown 只接受首尾带竖线的行与至少三横线的分隔行并保守排除全部元字符；表头 NFC 归一后必须唯一；违反语法安全性归为响应非法，安全但无法证明归属归为记录归属未证明）。同期一次后端清单提交把测试所需的 Schema 校验器显式声明为后端 devDependency——此前它只在根清单里，本地复合检出靠祖先 `node_modules` 提升而侥幸通过，独立安装的后端任务实际在测试注册前就模块解析失败。最后三个提交把线上 fail-closed 反馈闭环收口：分块概要不一致从 HTTP 502 精确改映射为 422，保留既有永久分类与只含版本号、期望计数、实际计数的冻结诊断，不新增任何隐藏修复调用；绑定器覆盖三处补齐（否定感知的状态分类器，不再把否定短语读成已结清；未激活卡片以独立闭集目标建模，金额类目标输出 `NOT_APPLICABLE` 而绝不回填 0，计入账户总数但排除在使用率与负债之外；无边界查询段只有在延伸到文档末尾、行满足同一受控词表严格证明且尾部被完全消费时才判定完整，否则继续 fail-closed），并把绑定器与查询策略的版本锚点同步到发布校验脚本；以及两项启动兼容与部署修复：持久化终态事件改为按"当前版本 + 历史上真实写出过的字符串"闭集校验（写入路径不变，非当前版本仍归一为 null），以及 PM2 重启前在子 shell 内先 source 当前环境文件——此前 `--update-env` 会把操作者 shell 的新发布变量注入进程，而 dotenv 不覆盖已存在的环境值，回滚后的旧代码因此以混合身份崩溃循环。

**为什么做**：概要表是唯一的自校验入口，"取第一张看起来对的表"等于放弃校验。OCR 侧的难点是供应商输出粒度粗且不可信：region 不能证明某个 cell 属于哪条记录，所以宁可失败也不能让模型自证归属。诊断状态码从 502 改 422 是为了让调用方能区分"证据永久不成立"和"上游基础设施故障"，而不是把它当成可重试。

**留下什么约束**：JPEG 预检是唯一的字节结构解析器，任何后续层都不得复制或弱化它；资源上限只能收紧不能放宽。表归属未证明与响应非法是两类错误，不得合并。HTTP 422 不能被描述为"已恢复"，它只是安全停止。绑定器与查询策略是版本锚定标识，改动必须同时更新发布校验脚本的字面断言。受保护内容演进要独立走基线切换。扫描 PDF 的 OCR 主链路在此阶段仍未接入路由、数据库与前端，即适配器功能边界完成不等于生产可用。

## 架构决策

以下决策从架构决策记录 ADR-0001 与仓库内合同、安全门禁文档提炼，并按实际演进顺序补齐了当时未写进 ADR 但被反复实现的两项。格式：背景 / 决定 / 放弃了什么 / 现在为什么这样。

### D1 双模型固定为唯一生产链路，并按组件切分权限

**背景**：证据优先的分析已经能对完整原生文字 PDF 建立文档清单、证据图、事实账本与确定性指标，但扫描 PDF 与图片缺少可绑定的结构化证据。仓库里已存在本地 OCR、轻量 OCR 身份补救与另一家视觉模型的代码，看起来"可以直接回退"。

**决定**：生产 OCR 供应商唯一固定为 `layout_parsing` 接口的 `glm-ocr`，事实提取模型唯一固定为单一 DeepSeek 型号。渲染、结构化适配器、证据绑定器与确定性规则按权限切分：OCR 只返回区域、候选文本与区域包围盒；适配器只做校验、排序、清洗与逻辑行/单元拆分；事实提取模型只从规范化文本提出候选事实；只有证据绑定器能把候选升级为 `accepted / unknown / absent / not_applicable / conflict` 五态；只有确定性规则能计算指标与评分，且不得调用模型。任一模型的单独输出不得进入 accepted facts、权威派生结果或权威缓存。原生文字 PDF 满足完整性门禁时 OCR 调用次数必须为 0。

**放弃了什么**：多 OCR 自动候补（同一文件会因供应商顺序、配置或瞬时错误产生不同证据身份，且缓存、错误、隐私与回滚都不可审计）；直接采用供应商 region JSON 或拼接文本（供应商 schema 与内部证据耦合，region 粒度不能证明表格单元与账户归属，纯文本又丢掉页、span 与包围盒）；允许模型为自己的候选"盖章"（构成自证循环，无法证明输入覆盖或金额归属）。零温度、JSON 模式、关闭思考或多次一致都不扩大任何组件的权限。

**现在为什么这样**：这条链路的可信度不来自模型精度，而来自"没有任何一环能替下一环作证"。多候补与自证都会把不确定性藏进结果里，而一旦分数出去就无法区分是真实结论还是静默填补。回滚 GLM 扫描能力时返回明确的不可用错误，不恢复旧 OCR 自动候补——这也是为什么旧代码可以留着但绝不接入路由。

### D2 三个业务终态，且文档级硬门禁不可降级

**背景**：全局发布门禁原本只有"完整成功"与"失败"两种输出。想允许用户局部核对已验证字段，就必须先定义第三终态，并保证文档级不可信不能借"部分结果"泄漏数字或绕过证据门禁。

**决定**：任务终态固定为 `succeeded` / `review_required` / `failed`。`succeeded` 要求文档硬门禁通过、执行与证据制品完整且事实、指标、决策依赖全部闭合，只有完整结果可进入权威缓存。`review_required` 要求文档硬门禁已通过、执行完成、证据与复核制品完整性完好，且仅在字段或指标级别存在 `unknown` 或 `conflict`；只允许输出合同定义的独立 accepted fact 投影，禁止总分、总体风险、产品匹配、顾问建议与债务执行建议，且必须使用独立的 review-only 命名空间与读取权限，禁止与权威缓存交叉命中。`failed` 覆盖文档硬门禁失败或不可评估，以及执行完成后才发现身份、覆盖、哈希或哈希链硬门禁失败的情形——此时不得展示任何分析数字，也不得缓存。租户与文档身份、页数与页序、全文覆盖、哈希与重放保护构成不可降级的文档硬门禁。

**放弃了什么**：放宽文档硬门禁以输出部分结果——身份、页数或哈希不可信时，任何局部数字都可能属于错误的用户或错误的文档。也放弃了"待复核至少要有 accepted fact"这种方便但无必要的约束。`queued` 与 `processing` 明确为非终态，避免中间态被当成结果缓存。

**现在为什么这样**：阶段 0 只接受这份目标合同；当时生产并不存在 `review_required`，在任务协议、持久化、缓存、恢复与 UI 分阶段完成前不能声明第三终态可用。这条"先冻结语义、再分阶段实现"的顺序，是后续每个阶段都能独立回滚的前提。

### D3 结构化证据契约不保存供应商信封，区域包围盒不得伪装成单元归属

**背景**：把 OCR 供应商响应直接存进证据对象最省事，但供应商响应里混着请求标识、用量、可视化图与裁图链接；同时供应商的 region 粒度远粗于表格单元。

**决定**：内部契约 `ocr-structured-v1` 只保留页、块、span 与区域级包围盒，供应商的 `id`、`request_id`、`usage`、可视化、裁图 URL 与原始响应体一律不进入证据与 canonical 字节。每个块必须带页内字符半开区间、区域内归一化包围盒、稳定阅读序与来源序号，并显式声明 `geometryGranularity: region` 与 `recordMembership: single-record / logical-table-row / non-record`。HTML 与 Markdown 表格必须由无网络、无脚本的确定性解析器拆成逻辑行与单元；无法证明多账户记录归属时返回"记录归属未证明"，而不是把整张表交给模型自己选归属。渲染 JPEG 字节与页标识是请求内校验状态，永不进入证据。结构 schema 校验通过不等于证据被接受。

**放弃了什么**：为粗粒度 region 伪造字符级或多边形级坐标；用"看起来能对上"的启发式补齐缺失行；在证据里保留供应商字段以便调试（调试信息一律留在合同之外）；以及把 generic 文本块标成单记录以让下游少报错。

**现在为什么这样**：region 包围盒只能声明"来自这个布局区域"。一旦 cell 继承了一个并不存在的 polygon，后续所有"我核对过位置"的说法都失真。把归属未证明做成显式状态，代价是更多明确失败与待复核，收益是不会产生伪精确的权威结果——这与 D2 的选择一致。

### D4 分析身份由实现源文件哈希推导，缓存按三个隔离加密域绑定

**背景**：长报告分析昂贵，缓存命中率高对用户很重要；但人工版本号会忘记递增，而共享缓存键下"甲的结果命中给乙"是真实风险。

**决定**：分析身份由提示与 schema 所在服务文件、规则引擎源文件、OCR 相关模块、依赖锁与证据账本实现文件的字节哈希共同推导——改任一实现即改身份，不依赖人记得改版本。权威缓存、任务作用域、任务暂存拆成三个彼此隔离的 AES-256-GCM 加密域，缓存条目密钥由租户、文档与分析身份共同导出，因此跨租户、跨文档、跨版本命中在构造上不可表达。只有 `succeeded` 的完整权威结果可进入权威缓存，`failed` 不缓存结果，供应商原始响应与任何模型的单独候选禁止跨请求或跨运行缓存。未来的分析身份还必须包含 OCR 供应商/模型/端点标识、适配器、渲染、阅读序、表格解析器与 schema 版本。

**放弃了什么**：可预测的全局缓存键与单层加密域（实现最简单，但跨租户命中只是"没碰上"而非"不可能"）；人工版本递增作为唯一身份来源；以及"为了命中率而放宽绑定"的任何折中。

**现在为什么这样**：这一选择把正确性成本前移到运行期，代价是改代码即解绑相关缓存、且加密域标识字符串被镜像断言锁定（改字符串必须同步改测试）。在首发无存量数据的前提下这个代价可以接受，但它换回来的是"缓存串档"这一类无法用功能测试发现的缺陷被结构性排除。

### D5 合同与门禁先于实现，且校验器不得自我见证

**背景**：目标架构写成的散文文档不能阻止漂移：受保护文件可以被改一个字节、CI 工作流可以删掉那一行调用、临时仓库的干净状态可以被忽略规则掩盖，而校验器自己报告 PASS。

**决定**：先冻结机器可读合同 JSON 与 JSON Schema，用 Schema 校验器加负例夹具（故意违规样本必须被拒）使其可执行，再把校验步骤接入 CI。校验器锚定内容而非形状——必需祖先 + 受保护 blob 集合 + 显式覆盖层，且模式选择不依赖分支名、环境开关或固定 HEAD。信任顺序被显式化：主校验器顶层只保留语言内建模块，全部 bootstrap 锚点通过之后才动态 import 被检查的可执行依赖。任何校验器都不能证明自己的字节：外部信任根固定为"干净提交号 + 独立完整 diff 审查 + 同一提交号的 CI 通过"，受保护内容的合法演进必须走一次独立审查的基线切换，而不是弱化字面检查。

**放弃了什么**：以分支名或环境变量选择校验模式（简单但可被伪造）；把校验器自哈希嵌进它自身（循环信任）；用"内部工作流字面锚已存在"替代服务端分支保护（若工作流删掉调用，校验器根本不会启动）；以及用新增忽略规则掩盖临时目录污染（掩盖即失效）。

**现在为什么这样**：这条决策是整段历史里最容易被外部读者低估的部分——它把"谁能证明通过"这件事本身当成设计对象。仓库公开后，这一层可以复用为 CI 完整性门禁的参考实现。

### D6 分阶段交付与单向回滚边界

**背景**：同时引入新模型接入、新终态语义与新业务评分口径，出问题时无法定位是哪一层漂移，也无法只回滚一层。

**决定**：按阶段 0（合同与安全门禁）、阶段 1（前端事实真相）、阶段 2（受信任支持事件链）、阶段 3（OCR HTTP 客户端）、阶段 4（结构化适配器）划分，每阶段独立 PR、独立发布、独立回滚；上一阶段被接受之后才开始下一阶段，多阶段共改的文件逐一做语义并集核验。回滚只能关闭本阶段新增能力：不得自动切回旧 OCR 候补，不得让复核制品进入权威缓存。业务评分口径的变更（例如未激活账户是否计分）与模型接入分属不同阶段，不合并决策。

**放弃了什么**：一次性大提交带来的一次性可验证性——这条链路放弃了"一个大 PR 更省事"，换取每一步都能被独立否证。也放弃了顺带决定的便利：在 OCR 上线时同时决定未激活计分被显式否决，因为它让模型接入与业务语义无法分别验证。

**现在为什么这样**：历史里最长的两次排障（合并后基线失效、启动兼容性崩溃循环）都发生在"多个阶段的标识同时演进"的交界处。分阶段本身不减少缺陷，但它决定了缺陷出现时能不能只撤一层。

## 演进中解决的问题

以下条目来自 fix 类提交与交接文档里的冲突账本，只保留有普遍工程价值的部分。

**1. 分块校验失败被误报成可重试的基础设施故障。** 多块分析的概要一致性校验失败时，统一的 catch 把所有合并拒绝都转成 5xx，客户端于是不断重试一个永久不成立的结论。解法是把这一个精确错误码单独映射为 422，保留其永久分类与"只含版本号、期望计数、实际计数"的冻结诊断，并显式禁止任何隐藏修复调用；其余分块失败维持原状态码。关键在于先区分"永久不成立"与"暂时不可用"，再谈诊断信息。

**2. 收紧版本校验导致历史数据让进程启动失败。** 存储层加载时按"当前版本标识"重新校验每一条已持久化的终态事件，上一版本合法写入的行被判为损坏，启动 fail-closed，服务直接不可用。解法是把校验集合从"当前值"改为闭集的"当前值 + 历史上真实写出过的值"，并保留原始字符串；写入路径不变，非当前值仍归一为空。这个区分让读侧兼容历史、写侧继续只允许当前版本。

**3. 回滚后进程环境混入新发布变量导致崩溃循环。** 部署脚本用 `--update-env` 重启进程，会把操作者 shell 里为"新版本"导出的变量一起注入；而 dotenv 的语义是不覆盖已存在的环境值，于是回滚后的旧代码看到"旧的发布标识 + 新的提交标识"这种混合身份，在身份闸门上反复自杀。解法是在子 shell 内先 source 当前版本的环境文件再执行重启，使进程环境与文件严格一致，与操作者 shell 状态解耦。这是"配置来源必须是唯一真相"的教科书案例。

**4. 概要表"取第一张看起来对的表"与状态语义分叉。** 文本回退在全局范围匹配行标签，于是官方表头之前出现的一张完整诱饵表会被选中；同时概要的活跃数用原始桶长度，而下游权威计算早已过滤掉已注销与已结清状态，两者永远对不上。解法是先枚举"表头有界、固定行序、四行完整"的候选并要求唯一基数——零张保持未知且不造 0，多张直接 fail-closed——并且只在活跃计数上复用权威状态谓词，总数与历史逾期口径保持不变。零候选与多候选是两种不同语义，混为一谈就会既漏报又误报。

**5. 否定短语被读成已结清，未激活账户被补成 0。** 状态正则匹配到了否定形式，把活跃余额清零并触发记录行不匹配；另一侧，未激活卡片没有可表示的状态，实现倾向填 0。解法是引入否定感知的闭集分类器，并把激活状态做成独立的受控集合目标，要求源行证明，金额类字段输出 `NOT_APPLICABLE`——计入账户总数，但排除在使用率与负债之外。这类问题的共同根源是"闭集里少一个状态，代码就会借用一个已有状态"。

**6. 无界查询段被当作完整读取。** 查询明细段落没有明确结束标记，读到一个无法识别的行就停止会悄悄丢数据。解法是把"完整"做成可证明条件：段落必须延伸到文档末尾、每行满足同一受控词表严格证明、且尾部（表头、页脚、锚定的收尾说明）被完全消费；任何无法识别的内容一律保持 fail-closed。同时把这类反复出现的线上失败按闭集码归档，避免归因到猜测的原因。

**7. 依赖提升掩盖了包未声明自己的测试依赖。** 根清单里声明的 Schema 校验器，在本地复合检出下通过祖先 `node_modules` 被解析到，测试本地全绿；只安装该包自身锁文件的独立任务则在测试注册之前就模块解析失败。解法是让该包在自己的清单里精确声明这个 devDependency，并用不含任何祖先 `node_modules` 的隔离工作树复验安装与解析。同批还断言"省略开发依赖时运行时文件仍可加载"，确认它确实是开发期依赖。

**8. POSIX 符号链接污染了临时 Git 仓库的干净状态。** 校验器的场景仓库把依赖桥建在仓库根：Windows 目录联接被 `**/node_modules/` 规则当目录忽略，而 POSIX 目录符号链接本身不是目录，同一规则下严格 untracked 检查精确报告它，于是干净性门禁在 Linux 上正确拒绝。解法是把依赖桥只在所有场景仓库的共同父目录建立一次，利用模块向父目录解析，并在每次克隆后用 `lstat` 断言仓库根不存在该目录。要点是拒绝通过新增忽略规则来"修好"这条断言。

**9. 较新 Git 接受的用法在旧版 Git 上不可移植。** 重放确定性合并树时，把每轮累计的裸 tree 对象直接作为 `merge-tree --write-tree` 的一侧，在新版 Windows Git 上工作、在旧版 WSL Git 上失败。解法是每轮先用累计树、固定父提交、固定中性身份与时间戳构造确定性 commit 字节，写入对象库后再传给原命令——不改索引、工作树、引用或配置。这样两个 Git 版本上得到同一棵锁定树，且不需要硬锁某个 Git 版本。

**10. 检查代码依赖了被检查对象，可执行顺序与信任顺序倒置。** 初版内容基线校验器在顶层静态 import Schema 校验器、密钥策略与夹具，而 CI 又先执行另一个仓库校验脚本：一旦某个受保护可执行文件被提交成"直接退出 0"或带副作用的内容，它就可能在基线锚点运行之前改变或结束进程。解法是顶层只保留语言内建模块，先用安全 Git 读取完成全部 bootstrap 锚点，任一失败立即非零退出，全部通过之后才动态 import 已锁定的策略与模块，并把该步骤在 CI 中前移。
